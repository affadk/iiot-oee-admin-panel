**Perhitungan (A2):** `src/utils/oeeCalculations.ts` **tidak berisi rumus OEE** — hanya `normalizeFsmState`, `formatDuration`, `parseServerMetric` (F2-1). Semua angka A/P/Q/OEE diterima apa adanya dari server (sesuai Build Guide §14.3 yang melarang hitung OEE di klien). Rumus A/P/Q eksplisit (pembilang/penyebut) tidak tertulis di kedua dokumen — hanya: pct = rasio dari total SUM (bukan AVG), `good = max(0, output − reject)`, kapasitas performance = `target_per_hour × operating_sec / 3600`. Satu-satunya rumus lengkap di repo ada di seed demo rollup (`demo/telemetry.ts:185-193`): `quality = good/total × 100`, `oee = avail × perf × qual / 10000`, `perf = null → oee = 0`. Rollup **bukan** SUM hourly di klien — dua respons server independen (F2-6).

**Refresh (A2):** `refetchAll` me-refetch 6 query paralel tanpa `await` (shift summary → hourly → timeline → downtime overlay → rollup → pareto kondisional); komentarnya mengklaim "BUKAN shift summary / downtime overlay" padahal keduanya di-refetch (G10). `isRefreshing` hanya mencakup 4 query (tanpa downtime overlay & pareto). Tombol Refresh **bukan** refresh rekonsiliasi (`POST /telemetry/reconciliation/refresh` tidak dipanggil). Master assets tidak ikut ter-refresh.

## Catatan di luar scope (tidak diusulkan sebagai pekerjaan panel)

1. **State FSM `SETUP` / `IDLE` (G25):** menambah state ke enum kanonis adalah perubahan backend (skema MQTT, CAgg, dan seluruh pembaca state). Panel hanya bisa menampilkannya setelah backend mengirimnya. Dicatat sebagai batasan rancangan: program pengurangan setup (SMED) tidak bisa diukur dari data ini hari ini.
2. **Definisi availability untuk jam planned penuh (G8, sisi server):** apakah jam yang sepenuhnya planned downtime harus dikeluarkan dari penyebut availability atau dilaporkan sebagai 0% adalah keputusan definisi backend/CAgg — panel hanya menampilkan apa yang dikirim server.
